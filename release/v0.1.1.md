## 背景

下游项目（dsh-kylin-pet M0 定妆照管线）把本插件当图像通道用，真机踩出两类问题：

1. **响应形态随机轮换，只认一种 → 孤儿产物**。同一模型（上游实为 Firefly 系）有时回标准
   `image_generation_call.result`（base64），有时把**预签名图片 URL 藏在消息 text** 里返回。
   `extractImageCalls` 只认前者 —— 解析扑空抛 BAD_RESPONSE，但图已经计费：钱花了、图丢了，
   本轮共产生 3 个孤儿。
2. **失败以普通字符串返回 → 被误判成功**。`img_generate` 的错误走普通文本结果（isError=false），
   下游编排（脚本 / 上游 agent）按「有输出即成功」判定，失败被吞。

## 修复

### 1. 文本 URL 兜底采集（`harvestTextImageUrls`）

- 标准形态缺席时，递归收集响应里**全部字符串字段**中的 `https://…`，
  按 **amazonaws / firefly / `/images/` 路径 / 图片扩展名** 过滤图像特征；
- 命中包装成 `{status:'completed', url}` 候选，走既有下载落盘链路；
- **边界**（都有用例钉住）：标准形态存在时不采集（revised_prompt 里的链接不得当第二张图）；
  同 URL 多字段去重；中文标点自然截断 URL；非图像特征的普通链接不捞。

### 2. `img_generate` 失败改抛错

- `kind === 'error'` 一律 `throw` —— 宿主注册表把抛错转成 **isError:true 结构化结果**
  （注册表源码：throwing listener → isError），文案含完整错误码与建议；
- **确认成本（confirm-required）是控制流不是错误**：仍按普通文本返回，模型读到后带
  `confirm=true` 重调 —— 这一半不能跟着改，另有用例钉住。

### 3. 附带

- `BAD_RESPONSE` 文案更新为「既没有 image_generation_call 项，也没有可辨识的图片 URL」
  （如实反映两种形态都已查过）。

## 验证

- **167 项测试**（新增 5 项：兜底采集 / 边界三条 / 双形态端到端落盘 / img_generate 抛错与确认流不抛），
  `tsc --strict` 零错误，上游数据对账通过；
- 端到端用例：响应只有「文本藏 URL」→ 采集 → 下载落盘 PNG，断言字节与下载请求。
